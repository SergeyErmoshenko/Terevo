# Раскладка дерева — почему так

Документ объясняет решения в пакете `layout`, которые не читаются из кода: почему выбран
алгоритм, какие визуальные дефекты он лечит и какими числами это подтверждено. Код комментариев
не содержит (см. `CODING_GUIDELINES.md` §1), поэтому первоисточник причин — здесь.

---

## Конвейер

```
GenerationAssigner  →  LayerOrdering  →  CoordinateAssignment  →  WalkerLayoutEngine  →  EdgeRouter
   поколения (y)        порядок в ряду      x-координаты            финальные rect        коннекторы
```

Основа — метод приоритетов (Sugiyama coordinate assignment в стандартном упрощении): каждая
группа притягивается к среднему положению **всех** своих реальных соседей, а не одного
«главного» родителя. Именно это удерживает вторые браки, кузенов и свойственников рядом с их
настоящим местом, а не там, куда их занёс рекурсивный обход.

---

## Почему коннекторы разводятся по каналам

`EdgeRouter` раздаёт каждой горизонтальной шине (`Bus`) собственный канал так, чтобы две шины с
пересекающимися x-диапазонами никогда не оказались на одном y.

До этого y шины считался только из низа родителей и верха ряда детей — значения одинаковые для
**всех** семей в одном междурядье. Любые две семьи с пересекающимися по x шинами рисовались по
одной и той же линии и сливались в один штрих.

Ключевая деталь: тест на пересечение отрезков этого **не видит** — коллинеарные отрезки формально
не пересекаются. На реальном дереве из 45 человек: строгих пересечений 0, фактических слияний
между семьями 6, максимум 1210 px. Пользователь описывает это ровно как «линии пересекаются».

Порядок раздачи — сначала самая широкая шина, чтобы самый длинный прогон остался в канале, ближайшем
к родителям, и типичная картинка не изменилась. Канал никогда не выходит за пределы междурядья:
если следующий канал упёрся бы в ряд детей, шина откатывается на базовый.

**Одна шина = одна скоба.** Дети одной родительской пары висят на общей перекладине, и это
намеренно: две ноги одной скобы обязаны делить чернила. Проверка обязана исключать такие пары по
**совпадению множества родителей**, а не по «есть общий родитель» и не по «тот же родитель» —
обе эти формулировки были опробованы и обе врут (см. §Проверки).

## Почему супруги всегда рядом

В одну группу (`Group`) попадают не только супруги, но и со-родители: двое людей с общим ребёнком
объединяются в общий бокс даже без зарегистрированного брака. Поэтому группа может содержать
больше одной брачной пары.

Если сортировать участников по одиночке — по притяжению к родителям или по имени — ничто не держит
супругов рядом, и посторонний со-родитель встаёт между ними. Тогда коннектор брака обязан перекрыть
третью карточку и рисуется **прямо через неё**.

Оба дефекта, найденные генеративным тестом роста, были именно такими: `Union(p7,p11)` через
со-родителя `p3` и `Union(p8,p11)` через `p15` (со-родитель `p11` по другому ребёнку). Отсюда
`marriageUnitsOf` — участники упорядочиваются целыми брачными единицами, всегда, включая случай,
когда ни у кого в группе нет родителей (раньше этот случай возвращал исходный порядок и пропускал
всю логику).

## Почему вершина рода выравнивается отдельно

`CoordinateAssignment.straightenSingleChildren` умеет выравнивать группу только по её **родителям**.
Группа без родителей не выравнивается никогда: сверху её ничто не тянет, и релаксация оставляет её
там, куда её положила первоначальная упаковка. В отчёте это выглядело как корень, стоящий в 482 px в
стороне от своего единственного ребёнка при свободном месте рядом, с коннектором через весь ряд.

`WalkerLayoutEngine.straightenLineageTops` закрывает этот случай и работает **по финальным
прямоугольникам**, а не внутри назначения координат. Причина: цель — x самого ребёнка, а позиция
участника внутри его группы определяется только в `orientedMembers`, уже после возврата из
`CoordinateAssignment`. Попытка нацелиться на центр группы ребёнка оставляла излом ровно в одну
карточку плюс `spouseSpacing` (замерено 192 px).

Сдвиг потребляет только уже существующий зазор и обязан спрашивать **тот же** `requiredGap`, которым
ряд упаковывали: между разными кластерами это `siblingSpacing + clusterSpacing`, а не просто
`siblingSpacing`. Резервирование одного `siblingSpacing` позволяло сдвигу занять 320 px, на которые
он не имел права, и неродственные ветки съезжались — то самое «наслаивается, если много создать».

Свободное место измеряется по **актуальным** позициям соседей, а не по исходным центрам: предыдущий
сдвиг в этом же проходе мог уже занять зазор. Чтение устаревших центров приводило к наложению
карточек (генеративный тест, seed 13: `p5` перекрыл `p8`).

## Проверки читаемости

Историческая ошибка набора тестов: утверждалось только «карточки не пересекаются». Это ничего не
говорит о **коннекторах**, а читают дерево именно по ним. Раскладка может пройти все проверки на
пересечение карточек и при этом рисовать две неродственные скобы по одной линии.

`me.terevo.testing.LayoutQuality` проверяет:

| Проверка | Что ловит |
|---|---|
| `assertNoCardOverlaps` | карточки друг на друге |
| `assertRowSpacing` | ряд, упакованный плотнее минимального зазора (не только строгое пересечение) |
| `assertOrthogonal` | диагональный сегмент — всегда баг маршрутизации |
| `assertSiblingsContiguous` | посторонняя карточка между родными сиблингами |
| `assertNoMergedBusLines` | коллинеарное слияние коннекторов разных скоб |
| `assertNoEdgeThroughCard` | коннектор через чужую карточку |
| `assertLoneRelativesAligned` | единственный родственник, брошенный в стороне при наличии места |

`GrowingTreeReadabilityTest` наращивает дерево по одному человеку теми же операциями, что даёт UI
(добавить ребёнка / супруга / родителя), и перепроверяет **всю** картинку после каждого добавления.
Seed фиксирован, поэтому падение воспроизводимо и печатает шаг с историей. Именно этот тест нашёл
оба дефекта с коннектором через карточку — на 11 и на 15 человеках; ни один написанный руками
сценарий их не воспроизводил.

Дефолт 40 seed × 30 шагов (~1200 состояний) — компромисс: проверка переразмечает дерево на каждом
шаге, поэтому 120 × 45 проходит, но занимает ~39 с и в обычный прогон не ставится.

### Чего проверять нельзя

Утверждения «неродственные ветки должны стоять на `clusterSpacing`» в наборе **нет**, и это
осознанно. Две попытки его написать дали ложные срабатывания:

* Отдельные деревья расставляются другим механизмом: компоненты размечаются независимо и
  стыкуются через `subtreeSpacing` (48 px). Это корректно и намного плотнее `clusterSpacing`, так
  что требование кластерного зазора через границу компонента помечает здоровую раскладку как
  сломанную (замерено: четыре отдельные семьи, все — «дефекты»).
* Внутри одного дерева «тот же кластер» означает общий корень по первичному родителю
  (`LayerOrdering.cluster`), а это не фиксированное число шагов по связям. Человек, у которого дед
  супруга — это дед соседа, принадлежит той же семье и законно стоит близко; двухшаговая проверка
  соседства назвала это дефектом на 92 px.

Воспроизводить настоящую карту кластеров в тесте — значит повторить продакшн-логику и не проверить
ничего. Визуально значимую часть закрывает `assertRowSpacing`.
