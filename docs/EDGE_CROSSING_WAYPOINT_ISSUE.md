# Известная проблема: пересечение линий на многопоколенческих (waypoint) рёбрах

**Статус: решена** (см. раздел «Решение» в конце). Ниже — исходное описание проблемы и неудачных
попыток, оставлено как история.

## Контекст: как рёбра вообще рисуются

Пайплайн раскладки (без изменений, не относится к этой проблеме):

```
TreeCanvasMapper.map / ExportTreeMapper.map
  → DirectionalLayoutEngine.layout / CachedLayoutEngine.layout
    → WalkerLayoutEngine.layout
      → GenerationAssigner.assign
      → по компонентам: LayerOrdering.order → CoordinateAssignment.assign → straightenLineageTops
  → EdgeRouter.route   (финальная геометрия линий)
```

Файл с проблемой: `src/main/kotlin/me/terevo/layout/EdgeRouter.kt`.

Ключевые понятия внутри `EdgeRouter.kt`:

- **Обычное (одно поколение) ребро** — родитель прямо над ребёнком, без промежуточных
  поколений. Рисуется как: вертикальный отрезок вниз от родителя → горизонтальная «шина»
  (`bus`) → вертикальный отрезок вниз в ребёнка. Высота шины — `busBetween()`, между нижней
  границей родителя и верхом ребёнка, с отступом `BUS_MIN_CLEARANCE = 28.0`.
- **`Bus`** (`data class Bus(val parents: Set<NodeId>, val childTop: Double)`) — ключ, который
  группирует ВСЕХ детей с одинаковым набором родителей И одинаковым `childTop` в один
  общий «мост»/скобку (`BusGeometry`). Это значит, что все прямые дети одного родителя на одной
  строке (например, у Андрея — Иван, Максим, Александр, «4», «5», Анна, второе «5») используют
  ОДНУ общую горизонтальную линию.
- **`assignBusChannels()`** — уже решает конфликты шина-vs-шина и (для прямых, не waypoint,
  рёбер) шина-vs-«стебель» (`Stem`) другого ребра, чтобы горизонтальная линия одной семьи не
  прошла сквозь вертикальную линию чужой. Это уже реализовано и работает (см. `allStems()`,
  `lowerBoundByX()`, комментарии в коде — там описан реальный кейс с Сусловым Василием
  Демидовичем, который уже исправлен).
- **Waypoint-ребро (многопоколенческое)** — когда ребёнок находится на несколько поколений
  ниже родителя (типичный кейс — прямая линия предок → далёкий потомок, минуя промежуточные
  поколения на графике). `WalkerLayoutEngine` строит для такого ребра цепочку `waypoints:
  List<Point>` — по одной опорной точке-«изгибу» на каждое промежуточное поколение. Высота
  каждого изгиба берётся из фиксированной формулы `generationTop - generationSpacing / 2`
  (середина зазора между поколениями), **без учёта** того, что происходит рядом по горизонтали.
  Финальный подход к ребёнку сглажен через `finalApproach()` (это уже исправленный в этой
  сессии баг «видимого излома» — трогать не нужно).
- **Критический архитектурный пробел**: waypoint-цепочка строится в `routeUnion()`/
  `routeParentage()` полностью НЕЗАВИСИМО от `assignBusChannels()`/`allStems()`. То есть вся
  система избежания коллизий (шина-vs-шина, шина-vs-стебель), которая уже работает для прямых
  рёбер, **вообще не применяется** к изгибам многопоколенческих рёбер.

Александру, а не просто идёт рядом.

## Что уже пробовали (и почему не получилось)

Идея: расширить существующую систему `Stem`/`allStems`/`assignBusChannels` (которая уже отводит
шины прямых рёбер от чужих стеблей) так, чтобы она же двигала Y каждого изгиба waypoint-цепочки в
сторону от стеблей соседних прямых рёбер.

Реализация (полностью откачена, в текущем `EdgeRouter.kt` её нет):

1. Добавлена функция `avoidStemCollision` + параметр `stems: List<Stem>`, прокинутый через
   `route()` → `routeUnion()`/`routeParentage()`.
2. В циклах построения waypoint-цепочки в `routeUnion`/`routeParentage` каждый `hopY` (высота
   очередного изгиба) проверялся на коллизию со стеблями прямых рёбер и сдвигался при
   необходимости.

Итерации и почему каждая проваливалась:

- **v1**: после сдвига `hopY` добавлялся корректирующий отрезок обратно к исходному
  `waypoint.y`. Это устраняло исходное пересечение (Андрей→Степан vs Андрей→Александр,
  `hopY` сдвинулся со 152 на 110), но сам корректирующий отрезок вводил НОВОЕ пересечение — с
  общей шиной другого сиблинга (Андрей→«5», шина на y=126, растянута на всю ширину семьи по x).
- **v2**: убрали корректирующий отрезок, несли скорректированную точку дальше
  (`current = Point(waypoint.x, hopY)` без возврата к исходному y). Проблема с той же шиной
  «5» просто переехала в `finalApproach` — финальный вертикальный спуск в ребёнка теперь сам
  пересекал ту же шину y=126, потому что x-колонка дамми-waypoint (2368, фиксирована
  `WalkerLayoutEngine`) целиком лежит внутри x-диапазона этой шины ([1551, 2560]).

**Причина, по которой это структурно не чинится локальным сдвигом Y одного хопа**: доступный
зазор для этого конкретного ребра — это диапазон [72, 232] (от низа родителя до верха следующей
строки, т.к. дамми делит строку с Александром). Внутри этого зазора:

- Стебель Александра занимает почти две трети снизу: [126.4, 232].
- Общая шина «5» — тонкая горизонтальная линия ровно на y=126, растянута на всю ширину семьи.

Единственный теоретически «чистый» интервал — [126, 126.4) — меньше пикселя и не даёт реального
зазора для отрисовки с разумным клиренсом. То есть **нет такого Y**, которое одновременно (а) вне
стебля Александра и (б) не совпадает с шиной «5». Любой локальный сдвиг одной точки просто
перекладывает пересечение с одного соседа на другого.

## Почему это не чинится «в лоб» ещё двумя способами

- **Сдвиг позиций узлов** — уже явно отклонён пользователем ранее в этой же сессии/работе (см.
  `docs/../.claude/plans/luminous-brewing-valiant.md`, если он ещё существует — там описан похожий
  тупик с `canonicalizeClusterOrder`: физически невозможно одновременно удовлетворить два разных
  требования по позиции для одного и того же узла).
- **Полноценное одновременное планирование путей** (a-la simultaneous multi-edge routing,
  potentially с горизонтальными обходами вокруг x-диапазона шины, а не только вертикальными
  сдвигами) — единственный вариант, который в принципе может закрыть проблему по-настоящему, но
  это значительно более сложная и рискованная переделка `EdgeRouter`, затрагивающая совместное
  разрешение позиций для потенциально всех рёбер сразу, не только соседней пары.

## Решение

Узлы не двигались, роутинг не переписывался — всё в `EdgeRouter.kt`:

1. **Первый изгиб waypoint-ребра садится на шину сиблингов** (`waypointSegments`, `siblingBus`).
   Если у тех же родителей есть прямые дети на следующей строке, их общая шина уже лежит в этом
   зазоре: ребро идёт по ней (коллинеарно) до своей dummy-колонки и только там уходит вниз. Ни
   параллельной второй линии, ни пересечения со стеблями сиблингов (они заканчиваются на той же
   шине). Андрей→Степан: изгиб с y=1838 переехал на шину y=1864, пересечение с Александром ушло.
   Тупик из прошлой попытки (нет свободного Y между стеблем Александра и шиной «5») этим
   обходится: подходящий Y — это сама шина.
2. **Последний подход к ребёнку садится на шину второго родителя**, если тот рисуется обычным
   одно-поколенным ребром, — обе линии входят в ребёнка по одной перекладине.
3. **Фиксированные горизонтали waypoint-рёбер занимают каналы** (`fixedWaypointRuns`) до раздачи
   каналов шинам — раньше шина могла прыгнуть прямо на них (воспроизводилось в
   `GrowingTreeReadabilityTest`, seed 3, шаг 29).
4. **Разнос шин**: конфликт шина-vs-шина проверяется по расстоянию, а не по точному равенству y;
   среди чистых каналов предпочитается отстоящий от соседних шин (и концов чужих стеблей) на
   `CHANNEL_SPACING = 26`, шаг сетки остался `MIN_CHANNEL_SPACING = 14`, так что ёмкость зазора не
   уменьшилась. Суслов Василий vs Кислицина→Михаил: было 14px, стало 28px.

Проверка на `project.terevo`: 0 пересечений (было 1). Тесты в `EdgeRouterTest.kt`: три новых теста
(сиблинговая шина, шина второго родителя, разнос шин) падают на старом коде и проходят на новом.

## Продолжение: Пётр, «5» и разнесение веток

- **«5» оторван от сиблингов**: проходная точка линии Андрей→Степан стояла в ряду между бездетными
  детьми Андрея. `LayerOrdering.keepLeafSiblingsTogether` выносит такую точку наружу, перепрыгивая
  только бездетных сиблингов с теми же родителями, так что число пересечений не меняется.
  Попытка собрать бездетных в блок ещё в `balancedOrder` каскадно сдвигала полдерева и откачена.
- **Кривая линия к Петру**: следствие «5», межкластерный зазор не оставлял Петру места над
  Кислициной. Теперь центры совпадают.
- **Ветки верхнего человека в разных колонках** (любое дерево): стороны считает
  `WalkerLayoutEngine.parentSides`. `CoordinateAssignment` упорядочивает кластеры сторон и добавляет
  ограничение в `compactClusters`; `straightenLineageTops` не заводит прародителя в чужую колонку;
  `keepSidesApart` — финальный жёсткий сдвиг, если зазор всё же мал. Инвариант
  `assertParentSidesApart` проверяется на каждом шаге `GrowingTreeReadabilityTest`, включая новый
  режим роста с упором на добавление родителей.
- Этот режим выявил ещё две проблемы, обе исправлены: шина, по которой едет многопоколенное
  ребро, распределялась по высоте без учёта продлённого участка; `straightenLineageTops` не видел
  колонки проходных точек многопоколенных линий.
