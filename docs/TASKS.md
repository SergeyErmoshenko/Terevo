# Фаза 1. Домен

## T-010 🔴 Идентификаторы и примитивы

**Цель.** Сделать невозможной подстановку id человека туда, где ждут id связи.

**Объём.**

* `@JvmInline value class PersonId(val value: Uuid)`, аналогично `RelationId`, `MediaId`.
* `PersonName` — value class с фамилией, именем, отчеством, девичьей фамилией; нормализация пробелов в фабрике.
* `Gender` — enum `MALE`, `FEMALE`, `UNKNOWN`.
* `EventDate` — sealed interface: `Exact(LocalDate)`, `Approximate(LocalDate, Precision)`, `Range(from, to)`, `Unknown`. Генеалогия почти всегда работает с неточными датами; `LocalDate?` здесь — ловушка, из которой потом не выбраться.
* `LifeSpan(birth: EventDate, death: EventDate)` с производным `isAlive`, `ageAt(date)`, валидацией `death >= birth`.
* Smart-конструкторы: `operator fun invoke(...): Result<T>` в companion, приватный конструктор. Невалидный объект нельзя создать в принципе.

**Готово, когда.** Юнит-тесты покрывают сравнение `EventDate` всех комбинаций (включая пересекающиеся диапазоны) и отказ создать `LifeSpan` со смертью раньше рождения.

## T-011 🔴 Модель человека

**Цель.** Иммутабельная запись о человеке, расширяемая без ломающих изменений.

**Объём.**

* `data class Person(id, name, gender, lifeSpan, birthPlace: Place?, deathPlace: Place?, notes: String, customFields: Map<String, String>, mediaIds: List<MediaId>)`.
* `Place` — value class со строкой + опциональными координатами (задел под карты).
* Все поля `val`, коллекции — `kotlinx.collections.immutable`.
* Никаких `lateinit`, никаких `var`, никакого пустого конструктора «для фреймворка».
* `customFields` и медиа объявляются сразу, даже если UI появится в фазе 5 — это избавит от миграции схемы.

**Готово, когда.** `Person` создаётся только через `Person.create(...)`, возвращающий `Result<Person>`; изменение — через `copy` в доменных функциях.

## T-012 🔴 Модель связей

**Цель.** Типы связей, которые нельзя перепутать и нельзя создать наполовину.

**Объём.**

* `sealed interface Relation { val id: RelationId }`.
* `ParentChild(id, parent: PersonId, child: PersonId, kind: ParentKind)`, где `ParentKind = BIOLOGICAL | ADOPTIVE | STEP | FOSTER`. Ограничение «не более 2 родителей» касается только `BIOLOGICAL`.
* `Marriage(id, spouseA: PersonId, spouseB: PersonId, since: EventDate, until: EventDate, status: MarriageStatus)`, `MarriageStatus = MARRIED | DIVORCED | WIDOWED | PARTNERS`.
* Симметрия супружества: нормализация пары (меньший id первым) в фабрике, чтобы `(A,B)` и `(B,A)` были одной связью и дубликат ловился примитивной проверкой множества.

**Готово, когда.** Тест: добавление `Marriage(B, A)` при существующей `Marriage(A, B)` возвращает ошибку `DuplicateRelation`.

## T-013 🔴 Агрегат FamilyTree и индексы

**Цель.** Одна структура, отвечающая за целостность всего графа, с O(1)-навигацией.

**Объём.**

* `class FamilyTree private constructor(persons: PersistentMap<PersonId, Person>, relations: PersistentMap<RelationId, Relation>, index: TreeIndex)`.
* `TreeIndex` — производные карты: `parentsOf`, `childrenOf`, `spousesOf`, `biologicalParentsOf`. Пересчитываются инкрементально при мутации, не с нуля.
* API: `addPerson`, `updatePerson`, `removePerson`, `addRelation`, `removeRelation` — каждая возвращает `Result<FamilyTree>` (новое дерево или ошибка). Персистентные коллекции делают копирование дешёвым.
* `removePerson` каскадно удаляет его связи и возвращает список удалённых, чтобы команда смогла себя инвертировать.
* Обход: `ancestors(id, depth)`, `descendants(id, depth)`, `bfs(from, edges)`.

**Готово, когда.** Property-тест: после произвольной последовательности из 1000 мутаций индексы совпадают с пересчитанными с нуля.

## T-014 🔴 Инварианты и валидация

**Цель.** Ни одна невалидная операция не доходит до БД.

**Объём.** Правила как отдельные объекты, реализующие `fun interface Invariant { fun check(tree: FamilyTree, change: Change): ValidationError? }`:

* `NoCycles` — новый `ParentChild` не должен создавать путь ребёнок → … → родитель. Проверка: `child` не должен быть в `ancestors(parent)`. Не пересчитывать весь граф — идти вверх от `parent`.
* `AtMostTwoBiologicalParents`.
* `NoSelfRelation` — человек не родитель и не супруг сам себе.
* `NoDuplicateRelation`.
* `ChronologyPlausible` — родитель рождён раньше ребёнка; разница ≥ минимального порога (12 лет, вынести в константу-конфиг); ребёнок рождён не позже смерти родителя + 1 год. Это **предупреждение**, а не ошибка: в реальных архивах даты бывают битые, блокировать ввод нельзя.
* Разделить `ValidationError` (блокирует) и `ValidationWarning` (показывается, но операция проходит).
* Реестр `Invariants.all` — список, по которому проходит `FamilyTree` перед применением изменения.

**Готово, когда.** На каждое правило есть позитивный и негативный тест; попытка сделать человека собственным прадедом возвращает `CycleDetected` с путём в сообщении.

## T-015 🔴 Ошибки как значения

**Цель.** Отказаться от исключений в бизнес-логике.

**Объём.**

* `sealed interface DomainError` с наследниками: `PersonNotFound`, `RelationNotFound`, `CycleDetected(path)`, `TooManyBiologicalParents`, `DuplicateRelation`, `InvalidDate`, `StorageFailure(cause)`.
* Собственный `Outcome<T>` или `kotlin.Result` с типизированной ошибкой — выбрать одно и не смешивать. Рекомендация: свой `sealed interface Outcome<out T> { data class Ok<T>, data class Err }` с `map`, `flatMap`, `getOrElse` — `kotlin.Result` не даёт типизировать ошибку.
* Исключения бросаются только на границах: битый файл, отсутствующий диск. Ловятся в адаптере и конвертируются в `StorageFailure`.

**Готово, когда.** В `me.terevo.domain` нет ни одного `throw`, кроме `error()` в недостижимых ветках `when`; это добавляется отдельной проверкой в архитектурный тест T-002.

## T-016 🔴 Команды и Undo/Redo

**Цель.** Каждое действие пользователя — объект, который умеет себя откатить.

**Объём.**

* `sealed interface Command { fun apply(tree: FamilyTree): Outcome<CommandResult> }`, где `CommandResult(tree: FamilyTree, inverse: Command)`.
* Реализации: `AddPerson`, `UpdatePerson`, `RemovePerson`, `AddRelation`, `RemoveRelation`, `Batch(list)`.
* Инверсия строится в момент применения, когда старое состояние ещё под рукой: инверсия `UpdatePerson(new)` — это `UpdatePerson(old)`; инверсия `RemovePerson` — `Batch(AddPerson(old) + AddRelation(каждая удалённая))`.
* `CommandBus(tree: MutableStateFlow<FamilyTree>, repository, undoStack, redoStack)`: применяет команду, пишет в БД в одной транзакции, кладёт инверсию в undo, чистит redo.
* Ограничение стека — 200 шагов, вынести в конфиг.
* `Batch` схлопывает связанную последовательность в один шаг undo (пример: «создать человека и сразу привязать к родителю» — один Ctrl+Z).

**Готово, когда.** Property-тест: для случайной последовательности из N команд `undo × N` возвращает дерево, равное исходному, и `redo × N` — равное конечному.

# Фаза 2. Хранилище

## T-020 🔴 Схема SQLDelight и миграции

**Цель.** Схема, переживающая обновления приложения.

**Объём.**

* Плагин SQLDelight, драйвер `sqlite-driver` (JDBC); сгенерированный код в пакете `me.terevo.persistence.db`, `.sq`-файлы в `src/main/sqldelight/me/terevo/persistence/db/`.
* Таблицы: `person`, `relation`, `person_custom_field`, `media`, `person_media`, `meta(schema_version, app_version, created_at)`.
* `relation` хранится одной таблицей с дискриминатором `type` и nullable-полями либо двумя таблицами `parent_child` / `marriage` — выбрать второй вариант: типобезопаснее, индексы уже.
* Индексы: `parent_child(parent_id)`, `parent_child(child_id)`, `marriage(spouse_a)`, `marriage(spouse_b)`, `person(surname, given_name)`.

* Миграции `1.sqm`, `2.sqm`, … с включённой верификацией (`verifyMigrations = true`).
* Даты хранятся как ISO-строка + признак точности (три колонки: `date_value`, `date_precision`, `date_to`), не как timestamp.

**Готово, когда.** `./gradlew verifySqlDelightMigration` зелёный; тест открывает БД схемы v1 и мигрирует на текущую без потери данных.

## T-021 🔴 Порты и адаптеры репозиториев

**Цель.** Домен работает с интерфейсом, ничего не зная про SQL.

**Объём.**

* В `domain.port`: `interface TreeRepository { fun load(): Outcome<FamilyTree>; fun apply(change: PersistedChange): Outcome<Unit>; fun transaction(block: () -> Unit) }`.
* В `persistence`: `SqlDelightTreeRepository`, маппинг «строка ↔ доменный объект» в отдельных `PersonMapper`, `RelationMapper` — мапперы это чистые функции, не методы сущностей.
* Загрузка дерева — батч-запросами (`SELECT * FROM person`, `SELECT * FROM parent_child`, …) и сборка индексов в памяти. Никаких N+1.
* Запись — только внутри транзакции; `CommandBus` открывает транзакцию на команду.
* Фейковая реализация `InMemoryTreeRepository` в `src/test/kotlin/me/terevo/testing/` — на ней гоняются тесты UI и домена. (В одном модуле `testFixtures` не нужны: тестовый sourceSet виден всем тестам.)

**Готово, когда.** Тест на 10 000 человек и 25 000 связей: `load()` < 2 с, сравнение загруженного дерева с исходным даёт равенство.

## T-022 🔴 Жизненный цикл проекта

**Цель.** «Создать / открыть / сохранить как / недавние» без сюрпризов.

**Объём.**

## T-023 🔴 Устойчивость к сбоям

**Цель.** Ноль потерянных подтверждённых операций.

**Объём.**

* `PRAGMA journal_mode = WAL`, `PRAGMA synchronous = NORMAL`, `PRAGMA foreign_keys = ON` при открытии соединения.
* Внешние ключи с `ON DELETE CASCADE` для связей — второй рубеж после доменной проверки.
* Периодический `wal_checkpoint(TRUNCATE)` при закрытии проекта.
* Автобэкап: копия файла в `<project>.backup/` при открытии, ротация на 5 копий.
* Тест на сбой: дочерний процесс делает N команд и убивается `SIGKILL`; после переоткрытия в БД ровно те команды, что успели закоммититься, файл целостен.

**Готово, когда.** Тест сбоя проходит 100 итераций подряд без повреждения БД.

# Фаза 3. Раскладка дерева

## T-030 🔴 Контракты раскладки

**Цель.** Отделить «где рисовать» от «чем рисовать».

**Объём.**

* Вход: `LayoutRequest(graph: TreeGraph, metrics: NodeMetrics, options: LayoutOptions)`. `TreeGraph` — узлы и рёбра в терминах id, без `Person`. `NodeMetrics` — размеры карточки. `LayoutOptions` — режим (предки/потомки/оба), глубина, интервалы.
* Выход: `Layout(nodes: Map<PersonId, Rect>, edges: List<EdgePath>, bounds: Rect)`.
* `layout` не знает про Compose: собственные `Point`, `Size`, `Rect` — три value class.

**Готово, когда.** Архитектурный тест подтверждает, что в пакете `me.terevo.layout` нет импортов, кроме stdlib.

---

## T-031 🔴 Разбиение на поколения

**Цель.** Определить вертикальный уровень каждого человека в графе, где могут быть несвязанные компоненты и браки между поколениями.

**Объём.**

* Слои через самый длинный путь: `generation(p) = max(generation(родителей)) + 1`, стартуя от людей без родителей.
* Обработка нескольких несвязанных компонент: раскладывать независимо, потом расставлять блоки по горизонтали.
* Выравнивание супругов: супруги тянутся к одному уровню; при конфликте (жена на поколение выше) приоритет у ветки с бо́льшим числом потомков, вторая связь рисуется наклонной.
* Алгоритм итеративный, без рекурсии — на 10 000 человек рекурсия положит стек.

**Готово, когда.** Тест на графе-«ромбе» (двоюродные брак) даёт корректные уровни; тест на 10 000 узлов не бросает `StackOverflowError`.

---

## T-032 🔴 Горизонтальная раскладка

**Цель.** Компактное дерево без наложений и с минимумом пересечений.

**Объём.**

* База — алгоритм Уокера (улучшенный Рейнгольд–Тилфорд) за O(n): два прохода, контуры поддеревьев, сдвиг подветвей.
* Адаптация под семейное дерево: пара супругов — один составной узел; дети центрируются под парой; повторные браки дают несколько групп детей у одного человека.
* Sibling spacing / subtree spacing / generation spacing — параметры, не константы в коде.
* Детерминированность: при равных условиях порядок узлов задаётся сортировкой по дате рождения, затем по id. Раскладка не должна «прыгать» между запусками.

**Готово, когда.** Golden-тесты: 8 эталонных деревьев (одиночка, пара, три поколения, повторный брак, усыновление, две компоненты, широкое дерево 200 сиблингов, глубокое 20 поколений) дают зафиксированные координаты; повторный вызов даёт бит-в-бит тот же результат.

---

## T-033 🔴 Прокладка рёбер

**Цель.** Читаемые линии связей, а не паутина.

**Объём.**

* Ортогональная маршрутизация: от родительской пары вниз до «шины» поколения, по шине вбок, вниз к ребёнку.
* Супружеская связь — короткий горизонтальный сегмент между карточками, маркер статуса (двойная линия — брак, перечёркнутая — развод).
* Небиологические связи — пунктир.
* `EdgePath` — список сегментов, а не готовый `Path` Compose: рендер отдельно.

**Готово, когда.** На эталонных деревьях число пересечений рёбер не превышает зафиксированного в golden-тесте.

---

## T-034 🔴 Инкрементальный пересчёт и кэш

**Цель.** Держать < 100 мс отклик при правке в дереве на 10 000 человек.

**Объём.**

* Кэш раскладки по хэшу структуры графа + опций.
* Правка полей человека (имя, дата) не меняет структуру → пересчитываются только размеры карточки, координаты остаются.
* Изменение связи → пересчёт только затронутого поддерева и его предков по цепочке контуров.
* Расчёт в `Dispatchers.Default`, результат — в `StateFlow`, UI не блокируется.

**Готово, когда.** Бенчмарк: правка имени на дереве 10 000 → < 10 мс; добавление связи → < 50 мс.

# Фаза 4. UI (MVP)

## T-040 🔴 Каркас приложения и тема

**Цель.** Оболочка, в которую вставляются экраны.

**Объём.**

* `App()` — корневой composable: меню (Файл, Правка, Вид, Справка), боковая панель, центральная область, статус-бар.
* Тема: `MaterialTheme` с собственными `TerevoColors`, `TerevoTypography`, `TerevoSpacing` через `CompositionLocal`. Ни одного захардкоженного `dp` или `Color` в экранах.
* Строки — через `Strings`-объект/ресурсы, готовность к локализации, без литералов в composable.
* Глобальные горячие клавиши: Ctrl/Cmd+N, O, S, Z, Shift+Z, F.

**Готово, когда.** Окно открывается с пустым состоянием «Создайте или откройте проект», меню работает.

---

## T-041 🔴 Инфраструктура MVI

**Цель.** Единый предсказуемый способ управлять состоянием экранов.

**Объём.**

* `abstract class Store<S, I>(initial: S)`: `val state: StateFlow<S>`, `fun dispatch(intent: I)`, `protected abstract suspend fun handle(intent: I, state: S): S`.
* Собственный scope на `Dispatchers.Main.immediate`, отмена при закрытии окна.
* Экранные состояния — `data class` с `val`-полями; всё производное (например, «можно ли нажать undo») вычисляется в состоянии, а не в composable.
* Intent — `sealed interface` на экран.
* Composable получают `state` и `onIntent: (I) -> Unit`, не сам Store — так они превьюшатся и тестируются.

**Готово, когда.** На тестовом Store есть тест «последовательность интентов → ожидаемая последовательность состояний» через `Turbine`/собственный коллектор.

---

## T-042 🔴 Холст дерева: зум и панорамирование

**Цель.** Плавная навигация по большому полотну.

**Объём.**

* `Canvas` с трансформацией «мир → экран»: `Matrix` из `scale` и `offset`, хранится в состоянии холста.
* Колесо мыши — зум к позиции курсора, а не к центру; drag ЛКМ по фону — панорамирование; трекпад-жесты на macOS.
* Пределы зума 0.1×–4×, кнопки «вписать в экран», «100 %», «к выбранному».
* Обратное преобразование экранных координат в мировые для хит-тестов.

**Готово, когда.** Зум и панорамирование держат 60 fps на дереве в 10 000 узлов (см. T-045 про отсечение).

---

## T-043 🔴 Рендер узлов и рёбер

**Цель.** Читаемая карточка человека и связи.

**Объём.**

* Карточка: ФИО, годы жизни, значок пола, миниатюра фото (фаза 5), метка «выделен».
* Рисовать через `DrawScope` (`drawRect`, `drawText` с `TextMeasurer`), а не композировать 10 000 `Box` — композиция таких объёмов не выдержит.
* Уровни детализации: при `scale < 0.3` карточка вырождается в прямоугольник с полосой цвета пола, текст не рисуется.
* Кэш измеренного текста в `TextMeasurer` — по id человека и версии его данных.

**Готово, когда.** Дерево из 10 000 узлов рисуется без пропуска кадров при панорамировании.

---

## T-044 🔴 Отсечение и производительность холста

**Цель.** Рисовать только то, что видно.

**Объём.**

* Пространственный индекс по узлам: равномерная сетка (проще R-дерева, для этой задачи достаточно), перестраивается вместе с раскладкой.
* Перед отрисовкой — выборка узлов и рёбер, пересекающих видимый прямоугольник, с запасом в один экран.
* Хит-тест клика — через тот же индекс, O(1) вместо перебора.

**Готово, когда.** Профилирование показывает, что число отрисованных узлов пропорционально площади экрана, а не размеру дерева.

---

## T-045 🔴 Выделение и навигация

**Цель.** Клик и быстрые переходы по родне.

**Объём.**

* Клик по узлу — выделение, подсветка узла и всех его рёбер; Esc — снять.
* Панель деталей справа: карточка выделенного человека, списки «Родители», «Дети», «Супруги» — клик по элементу переносит выделение и центрирует камеру с анимацией.
* История переходов: Alt+←/→.
* Двойной клик — открыть редактор.

**Готово, когда.** Переход к родителю центрирует камеру за < 300 мс анимации, выделение отражается и на холсте, и в панели.

---

## T-046 🔴 Форма человека

**Цель.** Создание и правка без потери введённого.

**Объём.**

* Диалог/панель с полями: ФИО, пол, дата рождения, дата смерти, место рождения/смерти, заметки.
* Ввод дат отдельным компонентом `EventDateField`: точная дата / «около» / диапазон / неизвестно.
* Валидация на лету через доменные smart-конструкторы; ошибка показывается у поля, кнопка «Сохранить» блокируется только при блокирующих ошибках; предупреждения (`ChronologyPlausible`) показываются жёлтым и не мешают.
* «Отмена» при несохранённых правках — запрос подтверждения.
* Сохранение уходит в `CommandBus` как `AddPerson`/`UpdatePerson`.

**Готово, когда.** Создание человека, правка и удаление проходят полный путь UI → команда → БД → обновлённое дерево на холсте.

---

## T-047 🔴 Редактирование связей

**Цель.** Управление родителями, детьми и супругами.

**Объём.**

* Из панели деталей: «Добавить родителя», «Добавить ребёнка», «Добавить супруга» — с выбором существующего человека (поиск по имени) или созданием нового в том же диалоге.
* Тип родительской связи выбирается (биологический/приёмный/…).
* Удаление и смена типа связи.
* Блокирующие ошибки инвариантов показываются понятным текстом: «Иван не может быть родителем Петра: это создаст цикл (Пётр → Мария → Иван)».

**Готово, когда.** Все негативные сценарии из T-014 воспроизводятся из UI и дают внятное сообщение, а не «error».

---

## T-048 🔴 Undo/Redo в интерфейсе

**Цель.** Ctrl+Z, которому доверяют.

**Объём.**

* Кнопки и горячие клавиши, привязка к `CommandBus`.
* Состояние кнопок из `undoStack.isNotEmpty()`.
* Подпись действия в меню: «Отменить: удаление человека».
* После undo камера центрируется на затронутом узле — иначе пользователь не видит, что произошло.

**Готово, когда.** Сценарный тест: 20 разнотипных действий, 20 undo, 20 redo, состояние БД и дерева совпадает на каждом шаге.

# Фаза 6. Продвинутое

## T-060 🟡 Калькулятор родства

**Цель.** «Кем мне приходится этот человек».

**Объём.**

* Поиск ближайшего общего предка двунаправленным BFS.
* Пара `(m, n)` — число шагов от каждого до общего предка — даёт каноническую степень: `m == 0 || n == 0` → прямая линия; иначе двоюродность `min(m,n) - 1` и колено `|m - n|`.
* Отдельно: свойство́ (родство через брак) — «шурин», «свекровь»; сводные и приёмные ветви помечаются.
* Русские термины таблицей `(m, n, gender, throughMarriage) → String` с fallback «родственник в N-м колене».
* Пакет чистый, без UI; в интерфейсе — «Определить родство» между выделенным и вторым выбранным.

**Готово, когда.** Тесты на 30 эталонных пар (двоюродный брат, троюродная сестра, дядя, племянник, прабабушка, шурин, свояченица…) дают ожидаемые термины.

## T-061 🟡 Статистика

**Цель.** Обзорные цифры по дереву.

**Объём.** Число людей, живых/умерших, средняя продолжительность жизни (только с известными обеими датами), распределение по поколениям, самые распространённые фамилии и места, число людей без дат/без родителей («что дозаполнить»). Отдельный экран, графики через Compose Canvas.

**Готово, когда.** Расчёт по 10 000 людям < 200 мс, значения совпадают с эталонными на тестовом наборе.

---

## T-062 🟡 Экспорт в PDF и изображение

**Цель.** Дерево на бумагу и в мессенджер.

**Объём.**

* PNG: рендер раскладки в offscreen-битмап с выбором масштаба и границ (всё дерево / видимая область / выделенная ветвь).
* PDF: тот же рендер векторно через PDFBox; разбиение большого дерева на страницы с метками стыковки.
* Экспорт использует тот же код рендера, что и экран — общая функция `drawTree(scope, layout, theme)`, вызываемая и из Compose, и из экспортёра.

**Готово, когда.** Дерево на 500 человек экспортируется в многостраничный PDF, текст в PDF выделяется (не растр).

---

## T-063 🟡 GEDCOM 5.5.1

**Цель.** Обмен с остальным генеалогическим миром.

**Объём.**

* Лексер строк GEDCOM (`level tag value`), сборка дерева записей, маппинг `INDI`/`FAM`/`BIRT`/`DEAT`/`MARR`/`NAME`/`SEX`.
* Кодировки: UTF-8, UTF-16, ANSEL (последний — таблицей перекодировки).
* Импорт: предпросмотр (сколько людей, семей, что не распознано), отчёт о пропущенных тегах, импорт одной `Batch`-командой (значит, откатывается одним Ctrl+Z).
* Экспорт: обратный маппинг, неподдерживаемые данные (произвольные поля) — в `NOTE`.
* Round-trip: импорт → экспорт → импорт даёт эквивалентное дерево.

**Готово, когда.** Три реальных `.ged` из открытых источников импортируются без исключений, round-trip-тест зелёный.

# Порядок выполнения

```
T-001 ─ T-002 ─ T-003 ─ T-004                      T-005 (по триггеру)
   └─► T-010 ─ T-011 ─ T-012 ─ T-013 ─ T-014 ─ T-015 ─ T-016
                                  │
                                  ├─► T-020 ─ T-021 ─ T-022 ─ T-023
                                  └─► T-030 ─ T-031 ─ T-032 ─ T-033 ─ T-034
                                            │
                                            └─► T-040 … T-048   (MVP)
                                                      └─► фазы 5–8
```

Домен пишется первым и полностью покрывается тестами до того, как появится первая кнопка. Это единственный порядок, при котором UI не приходится переписывать.
